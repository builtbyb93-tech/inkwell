# ADR-005: Vault scope, typed relationships and conversion provenance

Status: selected for the approved Phase 2 implementation; tests and PR evidence are recorded in its milestone report.

The directive makes the Idea Vault a workspace capture/retrieval system and permits multiple story/scene targets. Options were project-own every idea, or keep ideas workspace-owned with independently qualified destinations. Select workspace ownership: an idea may connect to stories/scenes in multiple projects owned by the account. Every association carries and validates its target project/story chain. A Story ID under the wrong Project, a Scene under the wrong Story/Project, or any foreign workspace fails. This does not permit cross-project canon/scene-to-canon relationships; those remain project-bound in later phases. Ideas do not silently become project canon.

Use separate IdeaStoryLink and IdeaSceneLink tables with composite scoped foreign keys and unique associations. Manual references can be removed with source-version preconditions; conversion references retain provenance and cannot be silently unlinked. Archive/restore changes the idea only and preserves all associations/targets. No permanent deletion API exists. Categories and tags are workspace-owned, deduplicated by normalized name, and linked through scoped FKs. Their paginated creation/selection supports classification; global rename/delete management is not added in this milestone.

All three conversions run in one transaction with the original idea preserved, a new target, its association where applicable, and an immutable IdeaConversion source snapshot/revision/content-schema version. Nullable typed target FK columns have a database CHECK requiring exactly one complete destination of the declared kind; there is no unguarded polymorphic type/id pair. Story seeds copy the full derived plain text into the existing synopsis field. Original formatting remains in the source idea and immutable conversion snapshot. Character and Scene seeds copy structured content independently. Editing the idea cannot silently rewrite a converted target or shared canon.

The dependency plan already includes minimal Character/Scene creation. Characters are shared project records only here; story-local/override management remains Phase 3. Scenes append to one story sequence, with parent locks, a sequenceVersion and unique (storyId,position). No groups, reordering, drag/drop, Bible management or Plot Board UI is shipped. Character/Scene overview pages are explicitly read-only. Later services must reuse the same scope and sequence constraints.

Lock order is Idea → Project → Story. Every mutation compares/increments the idea version. Conversion additionally requires a UUID Idempotency-Key, unique within the workspace, with a hash of source ID/version and qualified destination. Same-request retries return the original target; a reused key with different input returns 409. Replays return the version produced by the original conversion, never a newer version from an unrelated edit; a subsequent stale save must still conflict. Scene appends from different ideas serialize on their parent. Failure rolls back target, links, source revision and provenance together.

This is REST/server-domain behavior reusable by future native clients. No AI, fork, paid dependency, hosted storage resource or specialized publishing editor is required.
